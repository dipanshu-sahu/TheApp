Sent to the device during Step 4 of the TCP handshake
Broker URL
http://64.227.160.209:1883
Public MQTT broker endpoint. Sent as brokerUrl in Step 4.
mqttUsrName
deviceMac
The device's own MAC address is used as the MQTT username.
mqttUsrPswd
deviceId[0–2] + deviceMac[0–2]
First 3 chars of deviceId concatenated with first 3 chars of deviceMac.
lwtTopic
{siteId}/lwt
Last Will & Testament topic. Device publishes here on unexpected disconnect.
mqttPubTopic
{siteId}/pub
Device publishes telemetry / state updates to this topic.
mqttSubTopic
{siteId}/sub
Device subscribes here to receive commands from the cloud/app.
⚠️ Current state: All six MQTT values are placeholder strings in AddDevice.tsx lines 364–369. They must be replaced with the real siteId-derived formulas above before production.
Topic Namespace
All three topics are namespaced under siteId. This means every device within the same site shares the same pub/sub/lwt topic namespace — which is how the MQTT broker links device traffic to a site's logical scope.

TCP Provisioning Protocol
App ↔ Device over socket 192.168.10.1:3333 — 5-step sequential handshake
🔌 The device broadcasts its own WiFi AP. The app connects to it, then opens a TCP socket to 192.168.10.1:3333. All messages are JSON. Any response with status === -1 immediately aborts the flow.

6
Full UI Provisioning Journey
End-to-end flow from Home screen to device registered
🔐
Phase 0 — Pre-conditions
Authentication & Site Gate
  • User must be signed in — userId is required in every provisioning payload.
  • Site is mandatory. If no site exists, the user is redirected to create one before anything else happens.
📡
Phase 1 — ScanDevice Screen
Device Discovery
  • App requests ACCESS_FINE_LOCATION permission (Android requirement for WiFi scan).
  • WifiManager.loadWifiList() scans and displays nearby WiFi APs — device access points appear in this list.
  • Animated radar UI shown while scanning.
  • User taps a device from the scan results list.
  • AreaSelectionModal opens immediately.
📍
Phase 2 — AreaSelectionModal
Site & Location Selection
  • User picks a location from a grid (Bedroom, Hall, Kitchen, Bathroom…) or types a custom name.
  • App calls POST /api/sites with { userId, username, location }.
  • Server returns { siteId, location, … }.
  • On success → modal closes, navigation goes to AddDevice with { deviceSSID, deviceBSSID, siteId, location }.
🚧 Planned extension: A mesh selection step will be inserted here — show existing meshes for this site, allow creating new ones. Then show gateway/subgateway choices to determine deviceRole, gatewayMac, subGatewayMac.
🔑
Phase 3 — AddDevice: device_password step
Device AP Connection
  • User enters the device AP password (minimum 8 characters).
  • App calls WifiManager.connectToProtectedSSID(deviceSSID, password).
  • WifiManager.forceWifiUsage(true) — forces Android to route all traffic through the device AP, preventing smart-switching back to home network.
  • SSID verified by polling getCurrentWifiSSID() up to 6 times at 1.5s intervals.
  • On failure → goBackToScan with error message.
  • On success → select_wifi step; home network list loaded in background.
📶
Phase 4 — AddDevice: select_wifi step
Home WiFi Selection
  • Bottom sheet shows all home WiFi networks (loaded while user was entering device password).
  • User taps their home network → password field expands inline.
  • User enters home WiFi password (min 8 chars) and taps "Start Provisioning."
⚡
Phase 5 — AddDevice: provisioning step
TCP Handshake
  • Loading spinner shown ("Setting up your device").
  • TCP socket opened to 192.168.10.1:3333.
  • 5-step handshake executed sequentially (see Section 5).
  • Any error → goBackToScan with failure message.
  • Final ACK received → proceed to backend registration.
🔄 Connection Monitor: A NetInfo listener watches the connected SSID throughout phases 4 & 5. If Android drops the device AP, up to 3 silent reconnect attempts are made (2.5s back-off each). After 3 failures → goBackToScan.
✅
Phase 6 — Backend Registration
POST /api/devices
  • POST /api/devices called with full AddDeviceRequest payload.
  • Redux addDevice thunk dispatched; on success device is added to local state.
  • Navigation resets to Home screen.
  • Success toast: "Device added successfully! Your device has been added to the network."
